## 1. План 

1. **Понять модель.** Программа Solana — это код без собственных данных. Данные лежат в аккаунтах, которые передаёт вызывающий. Точка входа одна: `process_instruction(program_id, accounts, instruction_data)`.
2. **Выбрать минимум плюс.** По заданию достаточно лога. Для содержательности добавлены две инструкции (`hello`, `echo`): это заставляет разбирать `instruction_data`, а не только печатать строку.
3. **Определить формат данных.** Первый байт — тег инструкции, остальное — полезная нагрузка (для Echo — UTF-8 текст).
4. **Защита от некорректного ввода.** Пустые данные, неизвестный тег, не-UTF-8, текст длиннее 128 байт → `InvalidInstructionData`. Программа не паникует на плохом вводе.
5. **Тесты до деплоя.** Логика вынесена в `HelloInstruction::unpack`, поэтому проверяется обычным `cargo test` без сети.
6. **Клиент, зеркальный к программе.** Теги и лимит длины совпадают с Rust-кодом. Клиент дополнительно проверяет, что по Program ID лежит исполняемая программа.

## 3. Код программы

Файлы: `hello_solana/Cargo.toml`, `hello_solana/src/lib.rs` (в архиве).

Ключевые решения:
- `crate-type = ["cdylib", "lib"]`: `cdylib` даёт `.so` для сети, `lib` позволяет запускать тесты.
- `entrypoint!(process_instruction)` регистрирует точку входа.
- `msg!` пишет строки в лог транзакции (виден в Explorer как *Program Instruction Logs*).
- `enum HelloInstruction` и `match` по первому байту: стандартный паттерн Solana для разбора инструкций.
- Версия `solana-program` указана `2.3`: у неё самое низкое требование к версии Rust, она собирается с современными CLI. Если ваш `solana --version` другой мажорной версии и сборка ругается, выставьте ту же мажорную версию.
- Блок `[features]` и `[lints.rust]` нужен, чтобы макрос `entrypoint!` не выдавал предупреждений `unexpected cfg`.

## 5. Ваши шаги: от сборки до сдачи

1. **Тесты:** `cd hello_solana && cargo test` (ожидаете 4 passed).
2. **Сборка:** `cargo build-sbf`. Появятся `target/deploy/hello_solana.so` и `hello_solana-keypair.json`.
   - Если ошибка про версию lockfile (`lock file version 4 requires -Znext-lockfile-bump`): удалите `Cargo.lock` и пересоберите.
3. **Баланс и сеть:** `solana config get` (devnet), `solana balance` (для деплоя нужно несколько десятых SOL, с запасом возьмите 2–3).
4. **Деплой:** `solana program deploy target/deploy/hello_solana.so` → в выводе `Program Id: ...`. **Запишите его.**
5. **Проверка:** `solana program show <PROGRAM_ID>`; откройте `https://explorer.solana.com/address/<PROGRAM_ID>?cluster=devnet` (кластер Devnet!).
6. **Вызов:**
   ```bash
   cd ../client && npm install
   npm start -- <PROGRAM_ID> "Привет из Devnet!"
   ```
   Клиент напечатает signature, ссылку и логи. Ожидаемые строки в логе:
   `Program log: Hello, Solana! Program ID: ...`, `Program log: Accounts passed: 0`, `Program log: Echo: Привет из Devnet!`.
7. **Explorer:** откройте ссылку транзакции → блок *Program Instruction Logs* → скриншот.
8. **GitHub:** создайте репозиторий (или папку `week4`), загрузите код, заполните блок «Результаты сдачи» в README (Program ID, signature, ссылки, скриншот). Не публикуйте `id.json` и seed-фразу. `.gitignore` уже исключает `target/`.

## 6. Типичные ошибки и диагностика

| Симптом | Причина | Решение |
|---|---|---|
| деплой падает, «insufficient funds» | мало SOL | `solana balance`, `solana airdrop 2` или faucet.solana.com |
| программа деплоится «не туда» | сеть CLI не devnet | `solana config get`, `solana config set --url devnet` |
| нет `.so` / странные ошибки | `cargo build` вместо `cargo build-sbf` | использовать `cargo build-sbf` |
| клиент: «нет исполняемой программы» | неверный Program ID или кластер | сверить ID с выводом деплоя; кластер devnet |
| Explorer не находит транзакцию | выбран Mainnet | `?cluster=devnet` |
| `InvalidInstructionData` в логе | неверный тег или не-UTF-8 | использовать клиент из архива |

## 7. Самопроверка (ответы для защиты)

**Почему программа не хранит данные?** В Solana код и состояние разделены. Программа — исполняемый аккаунт без изменяемого состояния; данные лежат в других аккаунтах, которые вызывающий передаёт в инструкции. Благодаря этому рантайм заранее знает, какие аккаунты читаются и пишутся, и может исполнять непересекающиеся транзакции параллельно. В нашей программе аккаунты вообще не нужны (`accounts.len() == 0`).

**Что такое Program ID?** Это публичный ключ (адрес) аккаунта программы. Клиент указывает его в инструкции, чтобы рантайм знал, чей код вызвать. Он же приходит в `process_instruction` первым аргументом. При деплое он берётся из `hello_solana-keypair.json`.

**Что делает `entrypoint!`?** Создаёт функцию, которую вызывает рантайм, десериализует входные данные и передаёт их в `process_instruction`.

**Зачем тег в первом байте?** У программы одна точка входа, поэтому тип инструкции кодируется в данных; `match` по тегу выбирает ветку.

**Что произойдёт при неизвестном теге?** Вернётся `InvalidInstructionData`, транзакция отклонится, комиссия всё равно списывается.

**Почему `cdylib` и `lib`?** `cdylib` — для сборки `.so`, `lib` — чтобы тесты и клиентский код могли подключать крейт как обычную библиотеку.
